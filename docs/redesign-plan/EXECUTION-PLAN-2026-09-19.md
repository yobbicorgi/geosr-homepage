## 단계 1 — 사실·자산 인벤토리와 정보 구조

기존 사이트와 보존 자료를 대조해 필요한 것만 가져온다. 현 구현을 새 디자인의 시각 기준으로 삼지 않는다.

산출물:

- 상위 페이지 8개: Home, Business / Technology, Research / Results, Platform, Observation / Equipment, Company, News, Contact.
- Home 8단계 흐름: Hero Film, Field / Observation, From Data to Understanding, Technology / Capability, AX Platform, GeoDAP, Evidence, Company / Contact.
- 회사 대표 카피는 GeoDAP의 `Earth Data Intelligence` 문구를 재사용하지 않고 관측·분석·모델·AI·플랫폼까지 아우르는 GeoSR 전체 역량을 짧고 분명하게 표현한다.
- 기존 21개 기술 상세의 정확한 원문 명칭·식별자·현재 URL·상위 그룹·한국어/영어 콘텐츠·자료 출처를 담은 매핑표. 원문 대조 전에는 개수에 맞추려고 항목을 합치거나 명칭을 창작하지 않는다.
- 실제 장비·현장·사업·연구·학술·인증·면허·지식재산권·AX 캡처·GeoDAP 화면의 자산 인벤토리.
- 각 자산의 상태(`VERIFIED SOURCE`, `VERIFIED OUTPUT`, `EDITED SOURCE`, `CONCEPT`, `GENERATED CONCEPT`, `PLACEHOLDER`), 원본 경로/URL, 권리·출처, 사용 후보, 사실 검수 메모.
- 검증 전 정보 또는 콘텐츠를 이전하지 않는 모형 데이터 표기 규칙. 검색·필터, 빈 상태, 로딩, 오류, 준비 중 상태도 구분한다.

## 단계 2 — 세 개의 디자인 방향 비교

색상 바리에이션이 아닌 서로 다른 페이지 리듬과 정보 위계를 가진 3안을 만든다. 세 안 모두 같은 검증 자산·내용 범위를 사용해 비교가 가능해야 한다.

| 방향 | 구성 가설 |
|---|---|
| A — Cinematic Scientific | 영상과 장면 연결이 중심이며, 관측에서 분석까지 기술 서사를 크게 보여준다. |
| B — Spatial Editorial | 실제 현장·공간정보 자료와 편집형 타이포그래피가 중심이며 기술 근거를 탐색하기 쉽게 정리한다. |
| C — Interactive Technical | 관측→분석→모델→예측을 설명하는 인터랙션과 실제 플랫폼 화면이 중심이다. |

각 안은 1440, 1920, 2560 CSS px 데스크톱 전체 Home 수직 보드로 Hero, Field, Technology Story, Numerical / AI, AX, GeoDAP, Evidence, Contact를 보여준다. 이번 설계·QA 범위에서는 모바일 디자인과 검수를 제외하고 후속 범위로 둔다.

메인은 내부 비교를 위해 다음 가중 점수를 사용한다. 이는 성과·매출이나 사용자 연구 결과가 아니라 방향 비교용 판단 도구다.

| 평가 기준 | 가중치 |
|---|---:|
| GeoSR 브랜드가 첫 화면에서 명확한가 | 25 |
| 기술 표현의 사실성·현장 타당성 | 25 |
| 시각적 완성도와 페이지 리듬 | 20 |
| 정보 탐색과 콘텐츠 이해 | 15 |
| 모션·성능·접근성의 균형 | 15 |

사전 가설은 **B의 편집형 정보 구조를 중심으로, A의 Hero 연출과 C의 목적 있는 상호작용을 선택적으로 결합**하는 것이다. 이는 3안 비교 전 확정안이 아니다. 3안을 실제로 비교하고 점수 근거와 위험을 적은 뒤 메인이 추천안을 정한다.

완료 게이트: 각 안의 desktop 보드, 차이 설명, 점수 근거, 추천 방향을 제시한다. 모바일은 이번 범위에서 제외한다. 제안된 자동 진행 방식을 사용자가 수락한 경우 별도 “A/B/C 중 선택” 회신을 기다리지 않고 추천안을 다음 단계에 적용한다.

## 단계 3 — 추천 방향 상세화

추천 방향을 전체 사이트를 만들기 전에 검토 가능한 설계 명세로 구체화한다.

산출물:

- 페이지 맵, Home layout, navigation, 텍스트 위계, 한·영 카피 원칙.
- 색상·타입·그리드·spacing·container·미디어 비율·버튼/링크 규칙을 포함한 design tokens와 핵심 컴포넌트.
- 영상, 실제 사진, 제품 UI, 문서 자료, 제작 준비 중 화면의 배치와 상태 표시 규칙.
- 자격·신뢰 자료는 인증, 등록·면허, 지식재산권 3개 그룹으로 묶고 한 화면에서 읽을 수 있는 적정 밀도를 유지한다. 분류 전환은 간결한 수평 이동으로, 문서는 앞면을 계속 읽을 수 있는 제한된 rotateY로 표현하며, 확대 보기는 키보드 조작과 Escape를 지원하는 dialog로 제공한다.
- 모션맵: 무엇이 움직이는지, 왜 필요한지, 정적 대안과 reduced-motion 동작.
- 검색·필터 및 상세 페이지, 콘텐츠가 없는 항목의 명확한 placeholder 상태.
- 데이터·장비·지리·성과에 대한 사실 근거와 검수 책임.

완료 게이트: 브랜드 톤과 대표 페이지를 확인하고, 1440·1920·2560 CSS px desktop 화면 및 저모션 대안을 검토한다. 모바일은 이번 범위에서 제외한다. 이 검토 이후에만 ImageGen 정지 가안 등 승인된 제작 준비를 시작한다.

## 단계 4 — 영상·미디어 준비

웹 디자인과 병행하되 전체 영상을 한 번에 생성하지 않는다. 실제 근거 자산을 참조해 장비·현장과 카메라 동작을 재현하는 생성 영상도 허용한다. 단, 생성물을 실제 촬영이나 실제 분석 산출물인 것처럼 표시하지 않고, 지형·장비·센서 배치·데이터 레이어는 출처 대조와 사실 검수를 거친다. 측정값·모델 결과·기능 UI는 검증된 원자료 또는 후반 합성만 사용한다.

### 기업 영상 흐름

1. 지구·위성 관측에서 시작해 한반도와 북서태평양의 지리 맥락으로 이어진다.
2. 실제 연안·항만·하천과 육상 환경을 보여준다.
3. 실제 자료로 확인되는 조사선·USV·UAV/LiDAR·부이·센서·ROV 등 현장 관측을 연결한다.
4. 시료·실험실 분석, 수치모델, AI/원격탐사 해석을 거쳐 실제 플랫폼·공간정보 활용 장면으로 마무리한다.

장비 모양과 센서 구성은 실제 GeoSR 자료에 맞추고, 확인되지 않은 TPRBM 명칭이나 기능은 원자료 검증 전 쓰지 않는다. 사람이 없는 구도를 우선한다. 생성 이미지·영상에는 사람이나 손을 넣지 않는다. 사람이 있는 실제 원본은 출처와 사용 적합성을 확인하고 별도 승인된 경우에만 사용한다.

### AX 영상·플랫폼 기록

AX는 제품 경험에 한정해 `실제 문제 맥락 → Detect → Predict → Monitor → 실제 AX 화면` 순서로 검토한다. 서로 다른 AX 서비스가 자동으로 한 제품 워크플로를 이룬다고 주장하지 않는다. 가짜 UI·가짜 값·가짜 경보 결과는 만들지 않는다.

플랫폼 미디어는 기본 16:9다. 캡처 원본과 frame을 같은 비율로 준비해 전체 기능 화면이 잘리지 않고 빈 좌우 여백도 생기지 않게 한다. 단순히 `object-fit: contain`으로 맞춰 검은 여백을 만드는 방식에 의존하지 않는다. 실제 기능이 더 잘 읽히는 세부 화면은 16:9 구도로 별도 캡처·편집하고, 기능 맥락을 훼손하는 임의 크롭은 하지 않는다. GeoDAP 화면은 원본 화면비를 별도로 보존하고 왜곡·잘림 없이 배치한다. 주요 기능별 실제 3–5초 GIF/MP4 후보를 정리하며, poster와 정지·재생 제어를 제공한다.

### 제작 순서와 길이 후보

- Hero loop: 15–30초 후보.
- 기업 소개 film: 45–75초 후보.
- AX intro: 20–40초 후보.
- 장면별 실제 시작·중간·끝 reference frame → 지리·장비·과학 검수 → Flow 저화질 움직임 초안 → 검수·승인된 결과만 고품질 생성 또는 편집 → 실제 데이터/UI 후반 합성 → 웹 인코딩.
- ImageGen은 승인된 장면 가안을 만들고 메인이 시각·사실 기준으로 확인한다. Higgsfield는 메인이 직접 실행한다. 접근 가능한 구독·권한이 없으면 프롬프트와 제작 패키지만 준비하고 제작 완료로 표시하지 않는다.

검수 기준: 한국 지형의 위치와 해안선, 장비의 형상과 설치 위치, 샷 간 물리적 연속성, 자료 출처, 데이터 표현, 화면 내 텍스트·로고 여부를 전체 프레임에서 확인한다. 모든 콘셉트는 검증된 출력인 것처럼 사용하지 않는다.

완료 게이트: 장면별 storyboard와 reference 목록, 금지 요소, 화면비·길이·카메라 동작, 실제 데이터/UI 후반 합성 항목, 승인 상태가 기록되어야 웹 연결을 검토한다.

## 단계 5 — 대표 구현과 전체 페이지 확장

선택된 방향에 대해 먼저 Home과 AX의 대표 구간을 세로형 vertical slice로 구현하고 실제 브라우저에서 검토한다. 기존 파일이나 사용자의 변경을 덮어쓰지 않는다. 별도 작업 브랜치에서 시작하며 구현 전에 canonical 저장소 상태·기준 commit·변경 파일을 기록한다.

vertical slice 통과 후 Business / Technology, Research / Results, Observation / Equipment, Company, News, Contact, GeoDAP 진입을 확장한다. 기존 21개 상세 항목과 검색·필터 개념을 데이터로 유지하되, 확인되지 않은 상세 내용은 명시적으로 모형 또는 준비 상태로 구분한다. AX는 소개 페이지이고, GeoDAP은 별도 외부 서비스임을 탐색·링크 모두에서 명확히 한다.

한글·영문은 모두 자연스러운 문장으로 제공하고 언어 변경 시 현재 페이지와 가능한 경우 필터·검색 상태를 유지한다. 이번 구현 단계는 desktop 레이아웃만 설계하며 모바일은 범위에서 제외한다.

## 단계 6 — 품질·접근성·성능 검수

### 화면 폭

이번 단계 QA는 `1440`, `1920`, `2560` CSS px 데스크톱 폭에서 레이아웃과 자산 비율을 확인한다. Hero는 `100vh` fallback 뒤 `100svh`/`100dvh`를 사용해 정확히 한 viewport 높이로 유지하고, poster/video는 edge-to-edge cover로 표시한다. 각 폭의 첫 화면에서 다음 section이 보이지 않는지 확인한다. 모바일 QA는 이번 범위에서 제외한다.

### 기능과 접근성

- 한국어·영어 이동, 직접 URL 접근, 뒤로/앞으로, 검색·필터, 빈/로딩/오류/모형 상태.
- 모든 링크 목적과 외부 링크 표시, 죽은 경로·임시 문구·잘못된 화살표 점검.
- 키보드 순서와 focus, semantic button/link, 이미지 대체 텍스트, 대비, dialog Escape.
- `prefers-reduced-motion`, `save-data`, WebGL 미지원, 영상 자동재생 거부 시 핵심 콘텐츠 유지.
- 영상 재생/정지, 화면 밖 pause, poster, 로딩 fallback, 16:9 유지.
- 인증·면허·지식재산권 문서 분류, 앞면 가독성, 수평 분류 전환, rotateY 앞면 유지, 확대 dialog의 포커스·Escape 확인.
- 브라우저 콘솔, 네트워크 404, asset 경로, JavaScript 예외 확인.

### 성능

Poster-first, lazy loading, 화면 밖 영상 일시정지, 최소 preload, desktop 미디어 전략, 파일/구간별 정적 이미지와 동영상 예산을 설계한다. Lighthouse lab에서는 LCP·CLS와 TBT를 측정하고 환경과 결과를 기록한다. LCP ≤ 2.5초와 CLS ≤ 0.1은 목표값으로 둔다. INP ≤ 200ms는 현장 데이터(CrUX 또는 실제 사용자 모니터링)로 별도 평가할 field 목표이며, Lighthouse lab 점수로 대체하거나 보장하지 않는다.

완료 게이트: 1440·1920·2560 CSS px desktop, reduced-motion, 키보드, 한·영, 콘솔/404, media poster/재생, 빌드 결과를 QA 기록에 남긴다. 모바일은 이번 범위에서 제외한다. 미해결 이슈와 사실 자료 누락을 목록화한다.

## 단계 7 — 저장·동기화와 공개 승인

- 최종 diff와 작업 파일 목록을 검토해 사용자 변경이 포함되지 않았는지 확인한다.
- 관련 syntax/build/route/media 검증이 완료된 자체 변경만 commit한다.
- 사용자 승인된 GitHub 동기화 절차에 따라 remote/branch/HEAD/status를 재확인하고 push한 뒤 SHA를 기록한다. Downloads 경로는 별도 복사 대신 canonical을 가리키는 junction으로 확인한다.
- 로컬 preview 주소와 재현 절차를 결과에 기록한다.
- **공식 `geosr.com`의 교체·공개·배포는 별도의 최종 사용자 승인 전에는 진행하지 않는다.** 저장소 commit/push를 공개 사이트 배포로 간주하지 않는다.

## 역할과 실행 원칙

- 메인: 원본 우선순위와 사실성 기준을 해석하고, 각 디자인 보드의 구도·타이포그래피·페이지 리듬·모션맵을 상세 설계한다. 3안 비교와 추천, 승인 경계, 통합 검수와 최종 판단을 맡는다.
- Luna 구현 담당: 메인의 보드 설계와 지시를 바탕으로 보드·제작 산출물과 승인된 코드 범위를 실행한다. 상세 구현·시험을 연속 수행하고, 동일 파일 재조사를 피하며 변경 파일과 검증 결과를 메인에게 간결히 전달한다.
- 독립 병렬 작업이 유익할 때만 최대 2개 subagent를 사용하며 재위임하지 않는다. 변경 충돌 가능성이 있는 같은 파일은 병렬 할당하지 않는다.
- 확인되지 않은 사실은 미확인으로 기록한다. 사용자 자산과 기존 작업을 삭제·덮어쓰지 않으며 임시 파일을 작업 종료 전에 정리한다.

## 계획 수락 후 시작할 첫 작업

사용자가 이 실행 계획을 수락하고 “진행해”라고 하면, 메인은 먼저 원본 자료와 21개 기술 목록을 재검증하고 자산 인벤토리를 시작한다. 그 결과로 세 개의 desktop 디자인 방향을 실제 근거 자료에 적용해 비교하고 위 점수표로 추천안을 제시한다. 추천안을 선택한 근거와 남은 불확실성을 함께 기록한 뒤, 재확인 질문으로 작업을 끊지 않고 승인 범위 안에서 상세화·vertical slice·검수 순으로 이어간다. 공식 `geosr.com` 공개 배포만 별도 최종 승인 대기 대상으로 남긴다.
